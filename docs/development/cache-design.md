# 缓存扩展方向

[文档首页](../README.md) · [已有缓存 API](../query-cache.md) · [统一 Loader 提议](loader-design.md)

本文记录扩展边界，不新增公共 API。已有接口的使用、计费、失效和多进程规则以[查询块缓存](../query-cache.md)为准。

## 当前实现

- 调用方显式创建进程内 `BlockCache`，选择字节与条目预算。
- Reader 描述依赖 key，支持同步预取、共享源会话的 clone 和独立工作区。
- 命中复用解压块、prepared 索引或记录，不缓存完整窗口输出。
- `clear` 隔离在途提交；evict 后的 lease 保持有效并继续计费。
- 不准入的块走普通查询路径，缓存容量不是查询能否完成的前提。
- GTF / GFF3 整体常驻，quant 使用自己的窗口与内存预算，不直接套用 reader 缓存控制面。

## 后续协议需要解决的问题

| 方向 | 所需定义 |
|---|---|
| 异步 frame 发布 | 依赖描述、加载完成、取消、失败与重试、发布 generation |
| 外部 allocator | 分配与对齐、实际容量计费、lease 生命周期和释放责任 |
| 多级对象 | 压缩页、解压块、记录索引的依赖图与生成代价 |
| 已知访问序列规划 | lookahead、准入 / 淘汰决策、超大单块和预算不足时的回退 |
| 多源查询 | consensus 等组合查询的依赖合并和多个 source 的一致性 |
| 跨进程或磁盘缓存 | 可持久化身份、源内容校验、并发发布、崩溃恢复 |

上述能力均不能由现有 opaque key 推导为已经支持。namespace 是进程内源会话身份，不能直接作为持久化内容地址。

## 接入要求

普通查询继续自动分配结果，不应要求用户先制定缓存计划。缓存锁不覆盖读取、解压和输出拷贝；同 key 并发缺失应合并加载，失败后唤醒等待者。预算、在途分配和 lease 必须分别核算；不能通过将复制移到未计时阶段来宣称端到端加速。

性能验证应覆盖不开缓存、重复区域、重叠窗口、冷缺失、预算不足、并发 clone、clear / evict 与失败恢复。结果必须与同输入的无缓存查询一致。基准协议见[基准测试](../benchmarking.md)。
